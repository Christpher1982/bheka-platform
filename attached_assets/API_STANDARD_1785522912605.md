# API Standard

This expands CANON section 9 into CI-enforceable detail. The canonical API shape lives in
`schemas/api/openapi.yaml`, generated from Zod schemas per the anti-drift rule (CANON
section 14). This document states rules; it does not repeat the schema.

## 1. Base path and versioning

- Base path `/v1`. Version is in the URL path, not a header, so it is visible in logs,
  browser history, and support tickets without additional context.
- No breaking changes within a major version. A breaking change is: removing a field,
  changing a field's type, changing a field's meaning, removing an endpoint, changing an
  endpoint's success status code, or tightening validation on a previously accepted request
  shape.
- Additive changes (new optional fields, new endpoints, new enum values on
  already-designed-for-extension enums) do not require a version bump but must be
  documented in the changelog and must not be silently assumed safe by clients — new enum
  values in particular require clients to have a defined "unknown value" handling behaviour,
  stated in the OpenAPI schema description for that field.
- Deprecation policy: a `v1` endpoint or field marked for removal is announced at least 90
  days before removal, flagged via a `Deprecation` response header (per the IETF draft
  convention) and a corresponding entry in `CHANGELOG.md`, and removal only ever happens at
  a major version boundary (`/v2`), never silently within `/v1`.
- `/v2` is not created speculatively. It is created only when an accumulated set of breaking
  changes justifies a coordinated migration, with a stated `/v1` sunset date communicated to
  every integration partner and customer using webhooks or the public API at least 180 days
  in advance.

## 2. Errors: RFC 9457 problem details

Every error response uses `Content-Type: application/problem+json` per RFC 9457, which
obsoletes RFC 7807 and defines the standard fields `type`, `title`, `status`, `detail`, and
`instance`, plus API-specific extension members
([RFC 9457, Problem Details for HTTP APIs](https://datatracker.ietf.org/doc/html/rfc9457)).

Required fields on every error response:

| Field | Requirement |
|---|---|
| `type` | A URI identifying the problem type, resolving to `https://docs.bheka.io/errors/<slug>` internally documented; use `about:blank` only for generic, undifferentiated errors. |
| `title` | Short, human-readable summary, stable per `type` (does not vary per instance). |
| `status` | The HTTP status code, duplicated from the response line for logging convenience. |
| `detail` | Human-readable explanation specific to this occurrence. Must never include evidence content, key material, or another tenant's identifiers. |
| `instance` | A URI identifying this specific occurrence, typically `/v1/errors/<request-id>` correlating to the `audit_log` entry and trace ID. |

Bheka-specific extension members (namespaced, per RFC 9457 section 3.2's allowance for
extensions): `tenant_id` (the acting tenant, never a different tenant's ID even in error
detail), `trace_id` (OpenTelemetry trace correlation), `field_errors` (array of
`{field, code, message}` for validation failures, sourced directly from the Zod schema's
failure output).

### Error catalogue (representative; full catalogue lives in `schemas/api/openapi.yaml`)

| `type` slug | `status` | `title` | When used |
|---|---|---|---|
| `validation-failed` | 400 | Request validation failed | Zod schema rejects the request body, query, or path params. |
| `authentication-required` | 401 | Authentication required | No or invalid OIDC bearer token / agent mTLS certificate. |
| `step-up-required` | 401 | Step-up authentication required | WebAuthn step-up not yet completed for a Tier 3 evidence view or approval (CANON section 9). |
| `forbidden` | 403 | Insufficient permissions | RBAC check failed for the authenticated principal. |
| `not-found` | 404 | Resource not found | Includes the case where the resource exists but belongs to another tenant — RLS (ADR-016) means it is indistinguishable from non-existence, and the API must never leak that distinction. |
| `idempotency-key-required` | 400 | Idempotency-Key header required | POST creating a resource without the required header (section 4 below). |
| `idempotency-conflict` | 409 | Idempotency key reused with different payload | Same `Idempotency-Key` replayed with a materially different request body. |
| `rate-limited` | 429 | Rate limit exceeded | See `RateLimit-*` headers, section 6. |
| `tier-escalation-denied` | 403 | Tier escalation requires dual approval | Attempt to activate Tier 3 without two distinct approvers, one holding Information Officer role (CANON section 4). |
| `custody-tier-violation` | 409 | Operation not permitted under this tenant's key custody tier | E.g., attempting an Eride-side decrypt for a Tier B/C tenant (ADR-004). |
| `internal-error` | 500 | Internal server error | Unhandled exception. `detail` must never include a stack trace or internal file paths in production responses; full detail goes to the trace/log, not the client. |

- Every new error type added to a service must be added to this catalogue and to
  `schemas/api/openapi.yaml` in the same PR that introduces it; CI rejects an error response
  whose `type` is not present in the checked-in catalogue (verified via contract testing).

## 3. Authentication and step-up

- Human users: OIDC bearer tokens, short-lived access tokens with refresh, per CANON
  section 9.
- Agents: mTLS with a per-agent certificate issued at enrolment, never a shared bearer
  token or API key. Certificate revocation (device decommission, suspected compromise) is
  immediate and checked on every connection, not cached beyond a documented short TTL.
- WebAuthn step-up is required before any Tier 3 evidence view or approval action (CANON
  section 9). This is enforced server-side on the specific endpoints handling Tier 3
  evidence retrieval and approval submission — never assumed satisfied because the client
  claims it happened. A request missing a valid, recent step-up assertion receives
  `step-up-required` (401), not a silent downgrade to Tier 1/2 data.
- Step-up freshness: a WebAuthn assertion is valid for step-up purposes for a maximum of 5
  minutes from assertion time; a Tier 3 session spanning longer requires re-assertion.

## 4. Idempotency

- `Idempotency-Key` header is required on every `POST` that creates a resource (CANON
  section 9). Absence returns `idempotency-key-required` (400).
- The server stores `(tenant_id, idempotency_key) -> (request_hash, response, status_code)`
  for a minimum of 24 hours. A repeated request with the same key and the same request body
  hash returns the original stored response verbatim (same status code, same body), without
  re-executing the operation's side effects.
- A repeated request with the same key but a different request body hash returns
  `idempotency-conflict` (409) rather than either silently executing the new payload or
  silently returning the old response.
- Idempotency keys are scoped per tenant; the same key value used by two different tenants
  is not a collision (enforced via the `(tenant_id, idempotency_key)` composite key, which
  is itself subject to RLS per ADR-016).
- `PATCH`/`PUT` operations are idempotent by their nature (per HTTP semantics) and do not
  require the header, but `DELETE` on a resource that triggers non-trivial side effects
  (e.g., closing a case with cascading notification sends) does require it.

## 5. Pagination

- Cursor-based pagination only; no offset-based pagination on any list endpoint, since
  offset pagination degrades under concurrent writes and does not scale on
  high-volume-adjacent tables (evidence, detections, audit log).
- Query parameters: `?cursor=<opaque-token>&limit=<n>`, max `limit` is 200; a request for a
  higher limit is clamped to 200, not rejected, and the response indicates the effective
  limit applied.
- Response envelope includes `data` (the array), and `pagination: { next_cursor, has_more }`.
  `next_cursor` is opaque and must not be constructed or parsed by clients — it is not
  guaranteed to be a base64-encoded offset or timestamp indefinitely, and changing its
  internal encoding is not a breaking change as long as the contract (opaque token, pass it
  back unmodified) is preserved.
- Cursors are tenant-scoped; a cursor issued to Tenant A's session is rejected with
  `validation-failed` if presented under a different tenant's authentication context, to
  close a theoretical cross-tenant enumeration side channel even though RLS (ADR-016)
  should already prevent data leakage.

## 6. Rate limiting

- Every response, successful or not, includes `RateLimit-Limit`, `RateLimit-Remaining`, and
  `RateLimit-Reset` headers, following the `RateLimit` header field draft convention (CANON
  section 9 references RFC 9331 draft style; the field names above are the current draft
  convention and must be updated if the draft is superseded by a published RFC with
  different field names — track this as a living reference, not a frozen one).
- Rate limit scope is per-tenant-per-endpoint-class for human/API traffic (Redis-backed,
  CANON section 2) and per-agent-certificate for agent telemetry ingestion, so one noisy
  tenant or misbehaving agent cannot exhaust another tenant's quota.
- Exceeding the limit returns `rate-limited` (429) with a `Retry-After` header in addition
  to the `RateLimit-*` headers.

## 7. Audit logging

- Every privileged endpoint (anything beyond an unauthenticated health check) writes to
  `audit_log` before returning a response to the caller, per CANON section 9 — not
  asynchronously after the fact, so that a client receiving a success response is guaranteed
  the action is already recorded in the audit trail.
- The audit write includes: acting principal, tenant, endpoint, request `instance` ID
  (correlating to any error response if one occurred), and a summary of the action — never
  the full request or response body if either could contain evidence content or key
  material (see SECURITY_STANDARD.md logging rules).
- If the audit write itself fails, the request fails with `internal-error` (500) rather than
  succeeding without an audit record — a successful privileged action with no audit trail is
  treated as a correctness bug, not an acceptable degradation.

## 8. Webhook signing

Bheka sends webhooks for events a customer has subscribed to (via the `webhooks` table,
CANON section 8), such as detection or case-status changes surfaced to a customer's own
systems.

- Every webhook payload is signed using HMAC-SHA256 over the raw request body, with the
  signature delivered in a `Bheka-Signature` header in the format
  `t=<unix_timestamp>,v1=<hex_hmac>`, following the widely adopted timestamp-plus-HMAC
  pattern used by mainstream webhook providers to allow replay-window validation.
- The signing secret is generated per webhook endpoint at subscription time, shown to the
  customer once, and can be rotated on demand; rotation supports a dual-secret grace window
  (both old and new secrets accepted) for a configurable period, default 24 hours, so the
  customer's receiving endpoint can be updated without a delivery gap.
- Receivers are expected to reject any webhook where the `t` timestamp is more than 5
  minutes from current time, to limit replay-attack windows; this expectation is documented
  in the webhook integration guide, not silently assumed.
- Webhook delivery failures are retried with exponential backoff for up to 24 hours, after
  which the webhook subscription is marked degraded and the customer's admin is notified
  (`bheka-notify`); webhooks are never retried indefinitely in a way that could mask a
  permanently broken customer endpoint.
- Webhook payloads follow the same data-minimisation principle as API responses generally:
  they carry event metadata and resource references (IDs), not evidence content, so a
  compromised or misconfigured customer webhook receiver cannot become an unintended
  evidence exfiltration channel.

## AI implementation constraints
- Generated API route handlers must define their Zod request/response schemas first; the
  OpenAPI document is generated from those schemas, never hand-written independently.
- Generated error responses must use the exact `type` slugs from the catalogue in section 2
  and must not introduce a new error type without an accompanying catalogue and OpenAPI
  update in the same change.

## Required inputs
- Zod schema definitions per endpoint, from which `schemas/api/openapi.yaml` is generated.
- The full, current error catalogue (this document's section 2 is representative; the
  authoritative list lives in the OpenAPI document per the anti-drift rule).

## Expected outputs
- A single, generated `schemas/api/openapi.yaml` reflecting every `/v1` endpoint, error
  type, and schema, consumed by API documentation tooling and contract tests.

## Dependencies
- CANON section 9 (API standard), CANON section 14 (anti-drift rule), ADR-004 (custody
  tiers, for the `custody-tier-violation` error), ADR-016 (RLS, for `not-found` semantics).

## Acceptance criteria
- Given any endpoint returns an error, when the response is inspected, then its
  `Content-Type` is `application/problem+json` and its `type` field matches an entry in the
  checked-in error catalogue.
- Given a `POST` request creating a resource is sent twice with the same `Idempotency-Key`
  and identical body, when both responses are compared, then they are byte-identical and
  the resource was created exactly once.
- Given a webhook is delivered, when the receiver recomputes the HMAC over the raw body
  using the shared secret, then it matches the `v1` value in the `Bheka-Signature` header.

## Test checklist
- [ ] Contract tests verify every error response against the checked-in error catalogue;
      an undocumented `type` fails the build.
- [ ] Idempotency behaviour is tested for exact-replay, conflicting-replay, and
      cross-tenant-key-reuse scenarios.
- [ ] Pagination cursor opacity is tested by confirming a client-tampered cursor is
      rejected, not partially honoured.
- [ ] Rate limit headers are present and accurate on both 2xx and 429 responses.
- [ ] Webhook signature verification sample code is tested against the actual signing
      implementation to confirm the documented format is correct.
- [ ] Step-up (WebAuthn) enforcement is tested against every Tier 3 evidence and approval
      endpoint, not sampled.
