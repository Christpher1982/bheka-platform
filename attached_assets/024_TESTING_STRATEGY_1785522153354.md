# Testing Strategy

## 1. Why this document is unusual

Most testing strategies exist to catch functional regressions. Bheka has a second, heavier
obligation: it produces evidence that may be used to end someone's employment, and in some
matters may be presented to the CCMA or the Labour Court. A defect that silently corrupts a
timestamp, attributes an action to the wrong user, or breaks a hash chain is not a bug in the
ordinary sense. It is a defect that destroys the evidentiary value of the entire dataset and
potentially exposes the customer to an unfair dismissal finding.

That reframes the priorities. The highest-value tests in this system are not the ones that
prove features work. They are the ones that prove:

1. Evidence cannot be silently altered
2. Data cannot cross a tenant boundary
3. The agent cannot decrypt
4. Tier 3 cannot be activated without two approvals
5. Content never appears in a log, a trace, or an error message

Everything else is ordinary software testing and is treated as such.

## 2. Test pyramid and budgets

| Layer | Scope | Target count at v1 | Runtime budget | Gate |
|---|---|---|---|---|
| Unit | Single function or module, no I/O | ~2,500 | under 90 seconds | Every commit |
| Integration | Service plus its real datastores in containers | ~400 | under 8 minutes | Every pull request |
| Contract | Producer/consumer against schemas in `schemas/` | ~120 | under 2 minutes | Every pull request |
| End-to-end | Full stack, real agent binary, real Vault | ~60 | under 25 minutes | Merge to main |
| Security | Adversarial, property-based, fuzzing | continuous | nightly and weekly | Nightly; release gate |
| Performance | Load, soak, chaos | ~15 scenarios | nightly and weekly | Release gate |
| Manual exploratory | Human, scripted charters | 8 charters | one day per release | Release gate |

Coverage thresholds, enforced in CI and defined in `standards/CODING_STANDARD.md`:

- `eride-vault` and the `bheka-crypto` crate: **95% line, 90% branch**, no exceptions
- `bheka-agent`: **85% line**
- Backend services: **80% line**
- `bheka-console`: **60% line**, plus mandatory end-to-end coverage of privileged flows

Coverage is a floor, not a goal. A pull request that raises coverage while adding no
meaningful assertion should be rejected in review.

## 3. The five critical test families

These are non-negotiable and each has a dedicated suite that must be green before any
release. They map directly to the threats in `docs/003_THREAT_MODEL.md`.

### 3.1 Tenant isolation

The single most damaging possible failure. Row-level security is easy to get right in
development and easy to bypass accidentally in production through a connection that runs as
a superuser or a query that forgets to set the tenant context.

Required tests:

- For **every** table listed in `CANON.md` section 8, a generated test that creates two
  tenants, writes a row as tenant A, sets the session context to tenant B, and asserts zero
  rows returned. This test is generated from the DDL in `schemas/database/`, not hand-written,
  so a new table cannot be added without a corresponding isolation test.
- A test asserting that every application database role has `BYPASSRLS` **not** set.
- A test asserting that no migration grants `SUPERUSER` or `BYPASSRLS`.
- A ClickHouse equivalent asserting that every query path includes a `tenant_id` predicate,
  verified by parsing the generated SQL rather than by trusting the query builder.
- An API-level test that iterates every endpoint in `schemas/api/openapi.yaml`, authenticates
  as tenant B, requests a resource ID belonging to tenant A, and asserts HTTP 404 — never
  403, because 403 confirms existence.

### 3.2 The agent cannot decrypt

The security model in `docs/004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` rests on the claim that a
fully compromised endpoint yields nothing. That claim must be tested, not asserted.

Required tests:

- Static assertion that no private key type appears anywhere in the `bheka-agent` binary's
  type graph. Implemented as a compile-time trait bound plus a build-time symbol check.
- A test that dumps the agent's full process memory after sealing a payload and asserts the
  plaintext is absent, and that no X25519 private scalar is present.
- A test that takes a sealed blob from the agent's local SQLite buffer, hands it back to the
  agent process, and asserts the agent cannot open it.
- A test that extracts every secret the agent holds on disk and in memory, hands the full set
  to an attacker harness, and asserts the harness cannot decrypt a previously uploaded blob.
- A test asserting that credential and password field masking happens **before** encryption,
  by sealing a keystroke payload containing a known password string and asserting the string
  is absent after authorised decryption.

### 3.3 Evidence integrity and the audit chain

Required tests:

- Hash chain verification over a synthetic log of one million entries.
- A tamper test: modify one byte of one entry in object storage and assert verification fails
  and identifies the correct entry.
- A deletion test: remove one entry and assert verification fails.
- A reordering test: swap two entries and assert verification fails.
- An S3 Object Lock test asserting that a delete or overwrite attempt against a locked object
  fails, executed against a real bucket in COMPLIANCE mode, not a mock.
- A test asserting that every privileged endpoint identified in `docs/009_API_SURFACE.md`
  writes its audit entry **before** returning a response, verified by killing the process
  between the audit write and the response and asserting the audit entry survives.
- A chain-of-custody test asserting that an evidence record's SHA-256 hash, captured
  timestamp, device ID and sealing key identity are immutable after creation.

### 3.4 Authorisation, dual approval and separation of duties

Required tests:

- A generated matrix test over every role from `docs/007_RBAC_AND_IDENTITY.md` against every
  permission, asserting the exact expected allow or deny. Generated from the permission
  matrix so the matrix cannot drift from the code.
- Tier 3 activation with one approval: assert denied.
- Tier 3 activation with two approvals from the same person via two sessions: assert denied.
- Tier 3 activation with two approvals where neither approver holds the Information Officer
  role: assert denied.
- Tier 3 activation where the approver is in the requester's reporting line: assert denied.
- Tier 3 activation with a valid pair: assert allowed, assert a transparency notice is
  emitted, assert the notice is visible to the data subject.
- Evidence view without WebAuthn step-up: assert denied.
- Evidence view after the viewing session window expires: assert denied.
- An expired-case test: assert evidence linked to a closed case cannot be viewed.

### 3.5 No content leakage into telemetry

Bheka's own observability is a plausible route for customer evidence to escape. This is
tested by adversarial search rather than by discipline.

Required tests:

- A test harness that runs a full end-to-end flow with a distinctive canary string embedded
  in keystroke content, screen content, file names and clipboard content, then greps **all**
  of the following for the canary and asserts zero hits: application logs, OpenTelemetry
  spans and span attributes, metric labels, error tracker payloads, HTTP access logs,
  database slow query logs, NATS message headers, and any crash dump produced.
- A test asserting that every `Error` type crossing a service boundary is a
  `application/problem+json` document containing no evidence-derived field.
- A lint rule, enforced in CI, that forbids passing any type from the evidence domain to a
  logging function. See `standards/CODING_STANDARD.md`.

## 4. Rust agent testing specifics

The agent is the hardest component to test because it depends on operating system facilities
that behave differently in CI.

**Unit and property testing.** Use `proptest` for the parsing and buffering logic. The ETW
event decoder, the batching logic and the backpressure state machine are pure functions of
their inputs and must be property-tested, not example-tested.

**Fuzzing.** `cargo-fuzz` targets are mandatory for every parser that consumes data from
outside the agent's trust boundary: the ETW event decoder, the server response parser, the
policy document parser, and the update manifest parser. Fuzzing runs nightly with a minimum
of four CPU-hours per target and any new crash blocks the release.

**Unsafe code.** Every `unsafe` block requires a safety comment and a dedicated test. Miri
runs against the full test suite nightly. The policy in
`standards/CODING_STANDARD.md` is that `unsafe` is confined to the platform FFI modules and
is forbidden elsewhere.

**Platform matrix.** CI runs the agent test suite on Windows Server 2022, Windows 11,
Ubuntu 22.04 and 24.04, RHEL 9, and macOS 14 and 15. Windows 10 is included until its
support window closes.

**Load-shedding simulation.** This is a South African requirement and it is tested literally.
A test harness runs the agent under sustained telemetry load and terminates the container
without warning at randomised intervals, then asserts on restart that: the SQLite buffer is
intact, no sealed blob is partially written, no blob is lost, and no blob is uploaded twice.
Minimum one thousand kill cycles per release.

**Resource ceilings.** The budgets in `docs/011_ENDPOINT_AGENT_DESIGN.md` are asserted, not
aspired to. A soak test runs the agent for 72 hours under synthetic user activity and fails
the build if CPU, resident memory, disk footprint or network egress exceeds its stated
ceiling at any sample. Memory growth over the 72 hours must be flat within tolerance —
a leak in a process running on every endpoint in a bank is a production incident by
definition.

## 5. Backend testing specifics

**No mocked datastores.** Integration tests run against real PostgreSQL, real ClickHouse,
real NATS and real Redis in containers via Testcontainers. Mocking a database hides exactly
the class of bug that row-level security introduces.

**Zod at the boundary is the test.** Because `CANON.md` requires Zod validation at every
trust boundary and the OpenAPI document is generated from those schemas, contract tests
compare the generated document against the checked-in `schemas/api/openapi.yaml` and fail on
any difference. This makes schema drift a build failure rather than a runtime surprise.

**Migration testing.** Every migration is tested forward against a database seeded with
realistic volume, and every migration must be tested for the no-downtime patterns required by
`standards/DATABASE_STANDARD.md`. A migration that takes an `ACCESS EXCLUSIVE` lock on a
large table fails the build.

**Idempotency.** Every endpoint that accepts an `Idempotency-Key` is tested by replaying the
identical request ten times concurrently and asserting exactly one resource is created.

## 6. Security testing

| Activity | Cadence | Gate |
|---|---|---|
| Dependency vulnerability scan (`cargo audit`, `npm audit`, Trivy on images) | Every pull request | Blocks on high or critical |
| SAST (Semgrep with custom Bheka rules, `clippy` with deny warnings) | Every pull request | Blocks |
| Secret scanning (Gitleaks, pre-commit and CI) | Every commit | Blocks |
| SBOM generation and licence allowlist check | Every build | Blocks on copyleft |
| DAST against a staging deployment | Nightly | Reported, blocks on high |
| Fuzzing | Nightly | Blocks release on new crash |
| Miri on the agent and Vault | Nightly | Blocks release |
| Internal red team against the threat model | Per release | Blocks release |
| External penetration test | Before first paying customer, then annually | Blocks first customer |
| Cryptographic design review by an independent reviewer | Before first paying customer | Blocks first customer |

The cryptographic review is called out separately and deliberately. The design in
`docs/004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` was written in-house. It should not carry a
paying bank's evidence until somebody outside Eride who does this professionally has tried to
break it. Budget for this explicitly.

## 7. Performance and chaos testing

Targets below are **Provisional estimates**, not measurements. They exist so that the first
real measurement has something to disagree with.

| Scenario | Target | Status |
|---|---|---|
| Sustained ingestion | 10,000 endpoints, 50 events/second/endpoint | Provisional |
| Ingestion burst | 5x sustained for 10 minutes with no data loss | Provisional |
| Reconnect storm | 10,000 agents reconnecting within 60 seconds after an outage | Provisional |
| 30-day buffer drain | 10,000 agents each draining a full 30-day buffer | Provisional |
| Vault unwrap throughput | 500 DEK unwraps/second sustained | Provisional |
| Evidence view latency | p95 under 3 seconds to first frame | Provisional |
| Detection latency | p95 under 30 seconds from event to detection raised | Provisional |
| ClickHouse investigation query | p95 under 5 seconds over 90 days of one tenant | Provisional |

Chaos scenarios, run nightly against staging:

- Kill the Vault; assert the platform degrades to read-only on non-evidence functions and
  refuses evidence access cleanly rather than erroring obscurely
- Partition NATS; assert no telemetry is lost and agents apply backpressure
- Fill the agent's disk quota; assert graceful degradation to metadata-only and a clear alert
- Revoke a customer-managed key mid-session (custody Tier B); assert immediate lockout and a
  correct, non-alarming customer-facing message
- Simulate an `af-south-1` availability zone loss

## 8. Manual exploratory charters

Automation does not catch a confusing consent flow or a notice that reads as threatening in
isiZulu. Eight charters per release, each time-boxed to 90 minutes:

1. Enrol a new tenant end to end as a customer administrator who has never seen the product
2. Attempt to activate Tier 3 while trying to circumvent every control
3. Read every employee-facing notice as an employee, in each of the five languages
4. Attempt to exfiltrate evidence as a legitimately authorised viewer
5. Install, upgrade and uninstall the agent on a machine with an existing EDR product
6. Operate the product on a 3G-quality connection with intermittent loss
7. Complete a data subject access request as the data subject
8. Attempt to use the product to do something in the permanent refusals list

Charter 8 exists because a product's stated ethics are only real if somebody actively tries
to violate them and fails.

## 9. Definition of done for a testing perspective

A story is not done until:

- Unit tests cover the new logic to the service's threshold
- If it touches a tenant-scoped table, an isolation test exists and passes
- If it touches evidence, an integrity test exists and passes
- If it is a privileged operation, an audit test asserts the audit entry is written first
- If it accepts external input, a fuzz target exists
- If it can log, the canary leakage test passes
- The acceptance criteria in the story are expressed as executable tests, not as prose

## AI implementation constraints

- Do not write tests that mock PostgreSQL, ClickHouse, NATS or Redis. Use Testcontainers
  against real images. A mocked database cannot exercise row-level security, which is the
  primary tenant isolation control.
- Do not weaken or skip a failing test in the five critical families in section 3. If one of
  those tests fails, the implementation is wrong, not the test.
- Generate the tenant isolation matrix and the RBAC permission matrix tests from
  `schemas/database/` and the permission table in `docs/007_RBAC_AND_IDENTITY.md`
  programmatically. Do not hand-write them; hand-written matrices drift.
- Never write a test that constructs a private key inside `bheka-agent` for convenience.
  The agent has no code path that holds a private key, and a test that creates one invalidates
  the static assertion in section 3.2.
- Never include real customer data, real personal information, or a real production key in any
  fixture. Use generated synthetic data. This is a POPIA obligation, not a preference.
- Assert on behaviour, not on implementation detail. Tests that assert internal call sequences
  make refactoring expensive and catch nothing.
- Every performance target in section 7 is marked Provisional. Do not treat a failure against
  those numbers as a defect until the number has been validated by measurement; raise it for
  discussion instead.

## Acceptance criteria

- **Given** a new tenant-scoped table is added to `schemas/database/`
  **When** CI runs
  **Then** an isolation test for that table is generated and executed, and the build fails if
  the table is reachable across a tenant boundary

- **Given** the full set of secrets available to a compromised `bheka-agent` process
  **When** an attacker harness attempts to decrypt any previously uploaded sealed blob
  **Then** decryption fails

- **Given** a canary string is present in keystroke, screen, clipboard and file-name content
  **When** a full end-to-end flow completes
  **Then** the canary appears in zero log lines, zero span attributes, zero metric labels,
  zero error payloads and zero crash dumps

- **Given** a Tier 3 activation request with one valid approval
  **When** the request is evaluated
  **Then** it is denied, and denied again if the second approval comes from the same person,
  from someone in the requester's reporting line, or from a set containing no Information Officer

- **Given** one byte of one entry in the audit log object store is altered
  **When** chain verification runs
  **Then** verification fails and reports the specific altered entry

- **Given** the agent is terminated without warning one thousand times under load
  **When** it restarts each time
  **Then** the local buffer is intact, no sealed blob is partially written, no blob is lost,
  and no blob is uploaded twice

- **Given** the agent runs for 72 hours under synthetic activity
  **When** resource samples are taken throughout
  **Then** no sample exceeds the stated CPU, memory, disk or network ceiling, and memory
  growth is flat within tolerance
