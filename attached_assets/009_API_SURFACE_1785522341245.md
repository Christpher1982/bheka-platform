# API surface

This document explains the REST API in narrative form, grouped by resource.
The authoritative request and response shapes live in
`schemas/api/openapi.yaml`; this document does not restate them (CANON section
14). Two custom OpenAPI extensions carry information this document draws on
directly: `x-bheka-writes-audit-log` (true on every operation that writes to
`audit_log` before returning, per CANON section 9) and
`x-bheka-webauthn-step-up` (true on every operation that requires WebAuthn
step-up before it may proceed, per CANON section 9). Every path below is
relative to the versioned base path `/v1`.

## 1. API-wide conventions

- Errors are returned as RFC 9457 `application/problem+json` documents (the
  `Problem` schema in `schemas/api/openapi.yaml`), not ad hoc error shapes.
- Every POST that creates a resource requires an `Idempotency-Key` header
  (CANON section 9); `schemas/api/openapi.yaml` declares this as a shared
  header parameter rather than repeating it per operation.
- List endpoints use cursor-based pagination via `?cursor=&limit=`, with a
  maximum `limit` of 200 (the `PageInfo` schema and shared `cursor`/`limit`
  parameters in `schemas/api/openapi.yaml`).
- Rate limit state is communicated via `RateLimit-*` response headers on every
  operation, not documented per-endpoint here since it is uniform.
- Three security schemes are defined: `oidcBearer` for human users (OIDC bearer
  token), `agentMutualTLS` for enrolled agents (mTLS with a per-agent
  certificate), and `enrolmentToken` for the single unauthenticated-by-identity
  operation — initial agent enrolment — which instead presents a short-lived,
  single-use token issued out of band via the MSI `SecureCustomProperties`
  mechanism (CANON section 11).

## 2. Rate limit classes

Three informal classes exist across the surface, reflected in
`schemas/api/openapi.yaml` operation descriptions rather than as a separate
schema, since rate limit tuning is expected to change without being a breaking
API change:

- **Agent-facing** (`POST /agents/enrol`, `POST /agents/{agentId}/heartbeat`):
  highest expected call volume, scoped per-agent, tuned to tolerate the 30-day
  offline buffering and low-bandwidth batching behaviour in CANON section 16
  rather than penalising a device catching up after an outage.
- **Human interactive** (all `oidcBearer`-secured GET/PATCH/POST operations
  under normal console use): moderate limits scoped per authenticated user.
- **Privileged/sensitive** (evidence view, evidence export, approval grant,
  tenant key shred, user reidentify): tighter limits scoped per user
  regardless of tenant size, since these are exactly the operations a
  malicious insider (`docs/003_THREAT_MODEL.md`, T-INSIDER-01) would attempt
  to run at volume if a single credential were compromised.

## 3. Tenants

`GET /tenants/{tenantId}` and `PATCH /tenants/{tenantId}` expose tenant
profile and configuration; the PATCH writes to `audit_log`. `GET
/tenants/{tenantId}/key-custody-config` is read-only and does not write audit
log by itself (reading configuration is not a sensitive mutation), but `POST
/tenants/{tenantId}/keys/{keyId}/shred` is both audited and requires WebAuthn
step-up, consistent with crypto-shred being an irreversible, dual-authorised
act (CANON section 6, `docs/003_THREAT_MODEL.md` T-EVID-01). All tenant
operations require `oidcBearer` auth; there is no agent-facing tenant
endpoint.

## 4. Sites

Standard CRUD (`GET/POST /sites`, `GET/PATCH /sites/{siteId}`) under
`oidcBearer` auth. Create and update write to `audit_log`; reads do not.
Nothing in this resource requires WebAuthn step-up — site metadata is
operational configuration, not sensitive personal data or an irreversible
action.

## 5. Users, roles, and role assignments

`GET/POST /users` and `GET /users/{userId}` cover standard user management.
`POST /users/{userId}/reidentify` is the break-glass reidentification
operation referenced in `docs/003_THREAT_MODEL.md` (T-EMPLOYEE-01); it is both
audited and requires WebAuthn step-up, since it reverses whatever pseudonymity
protection is normally in place for a data subject. `GET /roles` lists
available roles; `GET/POST /users/{userId}/role-assignments` manages
assignment, with POST audited. Role assignment logic here is where the
Information Officer singleton constraint (`schemas/database/030_users_roles.sql`)
is enforced at the database layer; the API surface does not duplicate that
check, it simply surfaces the resulting error via the `Problem` schema if a
second concurrent Information Officer assignment is attempted.

## 6. Endpoints and agents

`GET /endpoints` and `GET /endpoints/{endpointId}` are read-only, `oidcBearer`
protected, human-facing fleet views. Agent operations are different in kind:
`POST /agents/enrol` uses the `enrolmentToken` scheme described above and is
audited, since enrolment is a security-relevant event even though it precedes
the agent having its own mTLS identity. `POST /agents/{agentId}/heartbeat`
uses `agentMutualTLS` and is not audited to `audit_log` — heartbeats are
high-frequency operational telemetry, not privileged actions, and are instead
observable via `bheka.agent.heartbeat.v1`
(`schemas/events/bheka.agent.heartbeat.v1.json`) and OpenTelemetry metrics.
`GET /agents/{agentId}` and `GET /agent-versions` are read-only human views.
`POST /agent-versions/{agentVersionId}/advance-ring` is audited: manually
advancing an update ring is exactly the kind of operator action that
`docs/003_THREAT_MODEL.md` T-SUPPLY-01 depends on being traceable.

## 7. Policies

`GET/POST /policies`, `GET/PATCH /policies/{policyId}`, and `POST
/policies/{policyId}/rules` are all `oidcBearer`-protected; every write is
audited. No policy endpoint requires WebAuthn step-up on its own — the step-up
requirement attaches to the consequence of a Tier 3-targeted rule (a case tier
escalation and its approval, see section 9), not to authoring the rule itself.
The database-level CHECK constraint forcing `requires_dual_authorisation = true`
for any Tier 3-targeted `policy_rules` row (`schemas/database/050_policies.sql`)
means the API cannot be used to create a rule that would bypass that
requirement even if an API-layer check were missing.

## 8. Detections and risk scores

`GET /detections`, `GET /detections/{detectionId}`, and `PATCH
/detections/{detectionId}` (used for triage state changes) are read-heavy with
one audited write. `GET /users/{userId}/risk-scores` is read-only. Neither
resource exposes a create endpoint directly — both `detections` and
`risk_scores` rows are produced by `bheka-policy` reacting to telemetry and
published as `bheka.detection.raised.v1` /
`bheka.risk.recalculated.v1` events, not created via the REST API by a human
or another service.

## 9. Cases, participants, and approvals

`GET/POST /cases`, `GET/PATCH /cases/{caseId}`, and `GET/POST
/cases/{caseId}/participants` follow the standard audited-write pattern. `POST
/cases/{caseId}/tier-escalations` is the request to raise a case's collection
tier and is both audited and step-up protected — this is the entry point for
the Tier 3 dual-authorisation workflow (CANON section 4). The escalation
itself does not take effect until the corresponding `approvals` are granted:
`GET /approvals/{approvalId}` is a plain read, while `POST
/approvals/{approvalId}/grant` is audited and step-up protected (granting is
the security-relevant act) and `POST /approvals/{approvalId}/deny` is audited
but does not require step-up (denial is not a privilege-granting action and
does not need the same assurance level). Only once all required approvals for
a `case_tier_escalation` are granted does `bheka-case` emit
`bheka.case.tier_escalated.v1`
(`schemas/events/bheka.case.tier_escalated.v1.json`); the API surface
intentionally does not expose a single call that instantly escalates a tier.

## 10. Evidence

`GET /cases/{caseId}/evidence` lists evidence metadata for a case; `GET
/evidence/{evidenceId}` reads metadata for one item. Neither requires step-up,
since metadata alone is not the sensitive payload. `POST
/evidence/{evidenceId}/view` and `POST /evidence/{evidenceId}/export` are both
audited and step-up protected: viewing content and exporting a court-admissible
bundle are the two actions the visibility-tier and evidence-integrity design
throughout `docs/003_THREAT_MODEL.md` (T-EVID-02) and
`docs/008_DATA_MODEL.md` section 5 is built to make fully traceable. A
successful view call is what produces an `evidence_views` row
(`schemas/database/080_evidence.sql`) and the corresponding
`bheka.evidence.viewed.v1` event.

## 11. Transparency and data subject requests

`GET /users/{userId}/transparency-notices` is a read-only view, used both by
administrators and by the employee-facing transparency portal (CANON section
16). `GET/POST /data-subject-requests` and `PATCH
/data-subject-requests/{requestId}` manage POPIA sections 23 to 25 requests;
both writes are audited. No endpoint in this group requires WebAuthn step-up —
these are rights-exercise and disclosure operations, not the sensitive
investigative actions the step-up requirement is reserved for.

## 12. Integrations and webhooks

`GET/POST /integrations` and `PATCH /integrations/{integrationId}` manage
connections to external systems (IdP, HRIS, SIEM, ticketing, WhatsApp Business
API, MDM); all writes are audited, none require step-up. `GET/POST /webhooks`
and `PATCH`/`DELETE /webhooks/{webhookId}` manage tenant-configured outbound
event delivery; all writes are audited. The webhook signing secret itself is
never returned by any GET (see the `IntegrationCreateRequest`/`WebhookCreateRequest`
schemas in `schemas/api/openapi.yaml`, which describe the secret as
write-only), consistent with treating webhook secrets the same as any other
credential material.

## 13. Endpoints requiring WebAuthn step-up (summary)

For quick reference, the complete set of step-up-protected operations, all
tagged `x-bheka-webauthn-step-up: true` in `schemas/api/openapi.yaml`:

- `POST /tenants/{tenantId}/keys/{keyId}/shred`
- `POST /users/{userId}/reidentify`
- `POST /cases/{caseId}/tier-escalations`
- `POST /approvals/{approvalId}/grant`
- `POST /evidence/{evidenceId}/view`
- `POST /evidence/{evidenceId}/export`

Every operation in this list is also audited. This set is deliberately short:
step-up is reserved for actions that are irreversible, that reveal sensitive
content, or that grant a privilege, consistent with CANON section 9's
requirement that step-up applies "before any Tier 3 evidence view or
approval" and this design's extension of the same bar to key destruction and
reidentification, which carry comparable severity.

## 14. Endpoints writing to audit_log (summary)

With the exception of `POST /agents/{agentId}/heartbeat` (high-frequency
telemetry, not a privileged action) and all read (GET) operations, every
mutating operation on the surface writes to `audit_log` before returning. This
matches CANON section 9's "every privileged endpoint writes to audit_log
before returning" and is enforced per-operation via the
`x-bheka-writes-audit-log` extension in `schemas/api/openapi.yaml`, which a
contract test should assert against the live implementation rather than trust
as documentation alone.

## AI implementation constraints

- Do not restate a request or response schema in this document. If a shape
  needs explanation, add or correct the `description` field in
  `schemas/api/openapi.yaml` and reference the operation here instead.
- Any new mutating endpoint must set `x-bheka-writes-audit-log: true` unless it
  is agent telemetry ingestion/heartbeat traffic, and that exception must be
  justified in this document, not silently assumed.
- Any endpoint touching Tier 3 evidence, key material, or reidentification must
  set `x-bheka-webauthn-step-up: true`; do not add such an endpoint without
  updating section 13 above.
- Do not implement tier escalation as a single-call operation. It must remain
  request-then-approve, matching section 9.

## Required inputs

- `schemas/api/openapi.yaml` as the sole source of truth for request/response
  shapes, security schemes, and the `x-bheka-writes-audit-log` /
  `x-bheka-webauthn-step-up` extensions.
- `docs/008_DATA_MODEL.md` for the underlying tables each resource group reads
  from or writes to.

## Expected outputs

- This narrative document, updated whenever a path, method, or extension flag
  changes in `schemas/api/openapi.yaml`.
- A contract test suite that asserts, for every operation, that the
  `x-bheka-writes-audit-log` and `x-bheka-webauthn-step-up` flags in the
  specification match actual server behaviour.

## Acceptance criteria

- Given this document, when cross-checked against
  `schemas/api/openapi.yaml`'s `x-bheka-writes-audit-log` and
  `x-bheka-webauthn-step-up` extensions, then sections 13 and 14 list exactly
  the matching set of operations, no more, no fewer.
- Given a new endpoint added to `schemas/api/openapi.yaml`, when this document
  is not updated to mention it, then that is treated as a documentation
  defect blocking merge.
- Given the rate limit classes in section 2, when implemented, then agent
  enrolment and heartbeat traffic is never throttled more aggressively than
  human interactive traffic during a legitimate post-outage catch-up burst.

## Test checklist

- [ ] Automated contract test confirms every operation flagged `x-bheka-writes-audit-log: true` actually produces an `audit_log` row in an integration test.
- [ ] Automated contract test confirms every operation flagged `x-bheka-webauthn-step-up: true` actually rejects a request lacking a verified step-up assertion.
- [ ] `POST /agents/{agentId}/heartbeat` is confirmed not to write to `audit_log`, and this is a deliberate, tested exception, not an oversight.
- [ ] Tier escalation is confirmed to require a separate grant call per approver before `bheka.case.tier_escalated.v1` fires, with no single-call shortcut in the implementation.
- [ ] Webhook and integration secret fields are confirmed absent from every GET response in the live implementation, matching the write-only schema description.
- [ ] Idempotency-Key handling is tested: replaying the same POST with the same key does not create a duplicate resource.
