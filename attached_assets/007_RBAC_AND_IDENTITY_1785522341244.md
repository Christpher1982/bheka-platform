## 0. Purpose

Every capability described in `004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md`,
`005_EVIDENCE_LIFECYCLE.md`, and `006_VISIBILITY_TIERS.md` is gated by a role. This
document defines every role, every permission, identity federation (OIDC), provisioning
(SCIM), step-up authentication (WebAuthn), and the separation-of-duties rules that make
dual authorisation actually mean something rather than two rubber stamps from the same
manager's team. Role and permission table structures live in
`schemas/database/` (`roles`, `role_assignments`) per `CANON.md` section 8's canonical
table list; this document does not restate column definitions, only the roles and
permission matrix in prose, since the matrix itself is the specification, not a schema.

## 1. Roles

Bheka ships nine standing roles. A tenant may assign multiple roles to one person, but the
separation-of-duties rules in section 5 constrain which combinations are usable together
for a given approval.

| Role | Summary |
|---|---|
| **Tenant Owner** | Commercial and billing owner of the tenant. Can manage tenant-level configuration, key custody tier selection (Tier A/B/C per `004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` section 1), and user provisioning. Does not automatically gain evidence-viewing rights. |
| **Security Administrator** | Configures policies, detection rules, integrations, and endpoint enrolment. Can open cases. Cannot unilaterally approve Tier 3 activation (needs a second approver per section 5) and cannot serve as the Information Officer approval on their own request. |
| **Investigator** | Works assigned cases: requests evidence access, reviews Tier 1/2 data, can request Tier 3 escalation (as a requester, not approver of their own request). |
| **Case Approver** | Authorised to serve as the "second approver" for Tier 3 activation and Tier 3 evidence access requests, alongside an Information Officer approval. Does not need to be a security specialist; this role typically sits with a senior HR or legal stakeholder. |
| **POPIA Information Officer** | The role defined by POPIA section 55 duties ([POPIA section 55](https://popia.co.za/section-55-duties-and-responsibilities-of-information-officer/)): encourages compliance with lawful processing conditions, handles data subject requests, and liaises with the Information Regulator. Inside Bheka, this role is additionally a **required second approver for every Tier 3 activation and every Tier 3 evidence access grant**, per `CANON.md` section 4. It is a distinct role from Security Administrator and Tenant Owner; a tenant may assign it to a person who also holds another role, but a single approval action cannot count as both the Information Officer approval and the "second approver" role — see section 5.2 for how dual counting is prevented. |
| **HR Partner** | Read access to case outcomes and Tier 1/2 evidence relevant to an open disciplinary process, no direct evidence-viewing rights beyond what a case grants, cannot approve Tier 3. |
| **Auditor** | Read-only access to `audit_log`, `approvals`, `evidence_access_grants`, `transparency_notices`, and `data_subject_requests` across the tenant. Cannot view evidence content itself, cannot change any configuration. Exists specifically so a compliance function or external auditor can verify the system's own claims without being granted the access being audited. |
| **Employee (data subject)** | Every monitored person has an implicit account of this kind for the purpose of receiving transparency notices and submitting data subject access requests (`018_NOTIFICATIONS_AND_TRANSPARENCY.md`). Not a console login role in the administrative sense; scoped entirely to the transparency and self-service portal. |
| **Eride Support Engineer** | Eride-side role (not a tenant role) used for support access. Never has standing evidence-view or key-unwrap capability; any Eride support access to tenant data is itself a break-glass-class event logged and disclosed per `004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` section 7.2 and 7.3. |

## 2. Permission matrix

Permissions are expressed as capabilities against the resources defined across
`006_VISIBILITY_TIERS.md`, `005_EVIDENCE_LIFECYCLE.md`, and
`004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md`. "Yes (2-of-2)" means the action requires the dual
authorisation described in section 5, not that either role alone can act.

| Capability | Tenant Owner | Security Admin | Investigator | Case Approver | Information Officer | HR Partner | Auditor |
|---|---|---|---|---|---|---|---|
| Manage tenant config, billing, key custody tier | Yes | No | No | No | No | No | No |
| Provision/deprovision users, assign roles | Yes | Yes | No | No | No | No | No |
| Author/edit policy rules (`016_DETECTION_AND_POLICY_ENGINE.md`) | No | Yes | No | No | No | No | No |
| Open a case | No | Yes | Yes | No | Yes | No | No |
| View Tier 1 evidence/metadata for an open case | No | Yes | Yes | No | Yes | Limited (case-scoped) | No |
| View Tier 2 evidence for an open case | No | Yes | Yes | No | Yes | No | No |
| Request Tier 3 activation | No | Yes | Yes | No | Yes | No | No |
| Approve Tier 3 activation (as one of two required approvers) | No | Yes* | No | Yes | Yes (mandatory as one of the two) | No | No |
| View Tier 3 evidence (post-approval, time-limited session) | No | No | Yes (if case-assigned) | No | Yes (if case-assigned) | No | No |
| Export evidence | No | No | Yes (with export approval) | No | Yes (with export approval) | No | No |
| Trigger break-glass | No | Yes | No | No | Yes | No | No |
| Change Vault authorization policy (M-of-N signer) | No | Yes (as one of N signers) | No | No | No | No | No |
| Trigger crypto-shred / retention destroy | Yes (with approval workflow) | No | No | No | Yes (POPIA s14 sign-off) | No | No |
| Read `audit_log`, `approvals`, `transparency_notices` | Yes | Yes | Case-scoped | No | Yes | No | Yes (full tenant) |
| Respond to data subject access requests | No | No | No | No | Yes | Supports, does not decide | No |
| Receive employee transparency notices as data subject | n.a. | n.a. | n.a. | n.a. | Yes (as oversight recipient, per `018_NOTIFICATIONS_AND_TRANSPARENCY.md`) | n.a. | n.a. |

\* A Security Administrator may serve as the non-Information-Officer half of a Tier 3
dual approval, provided they are not the requester and not in the requester's reporting
line (section 5). A Security Administrator can never substitute for the Information
Officer approval itself.

Detailed API-level scopes (which REST endpoints under `/v1` each role's OIDC token is
authorised to call) are defined in `schemas/api/openapi.yaml` security schemes, not
restated here per the anti-drift rule in `CANON.md` section 14.

## 3. OIDC

Human authentication into `bheka-console` and the `/v1` API is via OIDC bearer tokens, per
`CANON.md` section 9. Bheka acts as an OIDC relying party against the tenant's own
identity provider (Entra ID, Okta, Google Workspace, or any standards-compliant OIDC
provider) for Tier A/B customers who choose federated identity, and offers a Bheka-hosted
identity provider as a fallback for tenants without an existing IdP. Role assignment
(`role_assignments` table) is Bheka-side, mapped from OIDC claims (group membership,
department) at provisioning time or via SCIM (section 4) rather than trusting the IdP to
assert Bheka-specific roles directly, since Bheka's role set (section 1) is
product-specific and not something a generic IdP knows about.

Agents authenticate differently: mTLS with a per-agent certificate issued at enrolment
(`004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` section 4.3), never OIDC — an endpoint agent is not
a human session and should not be modelled as one.

## 4. SCIM provisioning

For customers with an existing identity provider, user and role lifecycle (creation,
deactivation, group/role sync) is kept in sync via SCIM 2.0
([RFC 7644, System for Cross-domain Identity Management: Protocol](https://datatracker.ietf.org/doc/html/rfc7644)).
Bheka exposes a SCIM server endpoint under `/v1/scim` (schema in
`schemas/api/openapi.yaml`) so the customer's IdP is the source of truth for who exists
and who has left, and deprovisioning an employee in the customer's IdP automatically
deactivates their Bheka role assignments and revokes standing sessions. This matters
specifically for the "approver may not be in the requester's reporting line" rule in
section 5.3: if the customer's IdP is the source of truth for org-chart/manager
relationships pushed via SCIM group or manager attributes, that data is what the
separation-of-duties check in section 5.3 evaluates against, so a stale manually-maintained
reporting-line list cannot silently become wrong after a re-org. Where a customer has no
SCIM-capable IdP, reporting-line data is entered manually by the Tenant Owner and is
correspondingly only as fresh as the last manual update — this limitation must be
disclosed to customers using manual provisioning.

## 5. Separation of duties

### 5.1 Requester cannot be an approver

No person can approve their own Tier 3 request or their own evidence access request. This
is enforced at the `bheka-case` and `eride-vault` layers (per
`006_VISIBILITY_TIERS.md` section 5 item 4), not only as a UI restriction.

### 5.2 Information Officer approval must be distinct and cannot be simulated

The mandatory Information Officer approval (`CANON.md` section 4, section 1 of this
document) must come from a person whose `role_assignments` row for that tenant includes
the POPIA Information Officer role. A Security Administrator or Case Approver who is not
also assigned the Information Officer role cannot satisfy this requirement, regardless of
seniority. A tenant with only one person capable of acting as Information Officer creates
an operational risk (that person becomes a bottleneck, or worse, a single point of
failure if unavailable) — tenants are advised to register a deputy Information Officer,
consistent with POPIA's own contemplation of deputy information officers
([Information Regulator guidance on Information Officer registration](https://inforegulator.org.za/portal-posts/)),
and Bheka's role model supports assigning the Information Officer role to more than one
person per tenant.

### 5.3 Reporting-line exclusion

An approver may not be in the requester's reporting line, in either direction (the
requester's manager, manager's manager, and so on up the chain, and equally a direct or
indirect report of the requester is disqualified from approving that requester's request).
This prevents a manager from ordering an investigation into their own team and then
personally rubber-stamping it, and equally prevents a subordinate from approving their own
manager's request under implicit pressure. Reporting-line data comes from SCIM-synced
manager attributes where available (section 4) or manual entry otherwise. Where reporting-
line data is missing or stale for a given user, the system fails closed: it refuses to
auto-clear a candidate approver rather than assuming no conflict exists, and surfaces the
gap to the Tenant Owner for manual confirmation before the approval can proceed.

### 5.4 Vault policy quorum is a separate separation-of-duties control

The M-of-N quorum on Vault authorization policy changes described in
`004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` section 7.1 is an Eride-internal separation-of-duties
control distinct from the tenant-facing Tier 3 dual authorisation in this section; the two
must not be conflated. A tenant's Information Officer has no ability to change Vault
policy, and an Eride Vault policy signer has no standing ability to approve a specific
tenant's Tier 3 case.

## 6. WebAuthn step-up

Per `CANON.md` section 9, WebAuthn is required as a step-up authentication factor before
any Tier 3 evidence view or approval action, regardless of how recently the user completed
their initial OIDC login. This means a valid OIDC session is necessary but not sufficient
for Tier 3 actions: the console additionally challenges for a WebAuthn assertion
immediately before rendering Tier 3 content or accepting a Tier 3 approval, and the
resulting step-up token is short-lived and scoped to that single action, not cached for
the rest of the session. This defends specifically against session hijacking or an
unattended, already-authenticated browser tab being used to approve or view Tier 3
material — a stolen session cookie alone is insufficient without also possessing the
user's registered authenticator (platform authenticator, security key, or passkey per the
[WebAuthn / Web Authentication specification](https://www.w3.org/TR/webauthn-3/)).

Step-up enrolment (registering a WebAuthn authenticator) is mandatory for any role in
section 1 that can approve or view Tier 3 material (Security Administrator, Investigator,
Case Approver, Information Officer); a user who has not enrolled an authenticator simply
cannot be granted those permissions in the console, independent of their assigned role.

## 7. Eride internal access

Eride Support Engineers and Eride operations staff have no standing role inside any
tenant's `role_assignments`. Any Eride-side access to a specific tenant's data (for
support, debugging, or incident response) is itself modelled as a break-glass-class event
per `004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md` section 7.2: time-boxed, logged to that tenant's
`audit_log`, and visible to the tenant's Auditor and Information Officer roles. This
closes the obvious gap where a vendor's own support staff become an unaudited backdoor
around the customer-facing RBAC model described in sections 1 through 6.

## AI implementation constraints

- Do not implement Tier 3 approval checks only in `bheka-console` UI logic; the check must
  be enforced server-side in `bheka-case` and again at the `eride-vault` policy enforcement
  point, so a UI bug or a direct API call cannot bypass dual authorisation.
- Do not allow a role assignment to be created for the Information Officer requirement
  that is satisfied by role name alone without checking the specific `role_assignments`
  row for that tenant; do not hardcode a specific username or hierarchy assumption.
- Do not implement reporting-line separation-of-duties as a soft warning; a disqualified
  approver must be blocked from submitting an approval, not merely flagged.
- Do not cache a WebAuthn step-up token beyond the single action it was issued for.
- Do not create any standing Eride-side role or credential with default access to tenant
  evidence or key material outside the break-glass path.

## Acceptance criteria

- Given a Tier 3 approval attempt with two approvals from the same reporting chain as the
  requester, when submitted, then the system rejects it before any Tier 3 collection or
  evidence access begins.
- Given a Tier 3 approval attempt where neither approver holds the Information Officer
  role, when submitted, then the system rejects it.
- Given a user without an enrolled WebAuthn authenticator, when they attempt to view Tier
  3 evidence or approve a Tier 3 request, then the action is blocked pending enrolment.
- Given a customer's IdP deactivates a user via SCIM, when the deactivation event is
  received, then that user's Bheka role assignments and active sessions are revoked.
- Given an Eride Support Engineer needs to access a specific tenant's data, when access is
  granted, then it is logged to that tenant's `audit_log` as a break-glass-class event
  visible to the tenant's Auditor and Information Officer roles.
