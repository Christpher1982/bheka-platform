# Bheka — Engineering Blueprint v1.0

> CONFIDENTIAL — Eride Technologies (Pty) Ltd. Not for distribution outside Eride
> Technologies or parties under written NDA. Contains proprietary architecture,
> threat models and commercial terms.

**Bheka** (isiZulu: to watch, to look after) is a POPIA-native insider risk management and
user activity monitoring platform built for the South African and broader African market by
Eride Technologies (Pty) Ltd, Ballito, KwaZulu-Natal.

This repository is the engineering blueprint. It is not marketing material and it is not a
pitch deck. It is the specification a developer or an AI coding assistant implements from.

---

## Read this first

### 1. `CANON.md` is the law

Every decision that must stay consistent across the whole system lives in
[`CANON.md`](CANON.md): the technology stack, the service names, the database table names,
the three visibility tiers, the three key custody tiers, the permanent product refusals,
the legal framework, the packaging formats. If any document in this repository contradicts
the canon, **the document is wrong and the canon wins**.

Read the canon before reading anything else. It is roughly 300 lines and it will save you
hours of confusion.

### 2. Every document declares its status

This blueprint was written before the product existed. Parts of it are decided and parts of
it are educated guesses. Rather than write the whole thing in a uniform confident voice and
leave you to guess which is which, every document declares one of three statuses in its
front matter:

| Status | Meaning |
|---|---|
| **Locked** | Decided. Changing it requires a new ADR that supersedes the old one. |
| **Provisional** | Best current answer. Expected to change when a named dependency resolves. The dependency is stated in the document. |
| **Open** | A known gap, deliberately unresolved. The open question is stated explicitly. |

If you are conducting technical due diligence or a security review, the Provisional and Open
markers are the honest part. Read them first.

### 3. Prose never restates a schema

The single most common failure of a large specification is drift: the `evidence` table has
seven columns in one document and nine in another, and nobody notices until it has been
built twice. This repository forbids it.

- Database truth lives **only** in `schemas/database/*.sql`
- API truth lives **only** in `schemas/api/openapi.yaml`
- Event payload truth lives **only** in `schemas/events/*.json`
- Policy rule truth lives **only** in `schemas/policies/*.json`

Documents reference these files by path. A prose document that repeats a column list is a
defect, and should be raised as one.

## The short version of the architecture

- A **Rust agent** on Windows, Linux and macOS collects telemetry. It holds only a tenant
  X25519 **public** key. It seals every payload under a random per-blob key using HPKE.
  A fully compromised endpoint cannot decrypt anything, including its own prior uploads.
- A **TypeScript/Node backend** ingests, detects, scores, and manages cases.
- **Eride Vault**, written in Rust and running in a separate cloud account, is the only
  component that can unwrap data encryption keys. It never sees bulk payloads.
- Collection runs at one of **three visibility tiers**. Tier 1 is metadata only.
  Tier 3 — which includes keystroke content — is off by default and requires two approvers,
  one of whom must be the customer's POPIA Information Officer.
- The person being monitored can see that they were monitored. This is the product.

Read [`docs/002_SYSTEM_ARCHITECTURE.md`](docs/002_SYSTEM_ARCHITECTURE.md) for the real
answer, and [`docs/004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md`](docs/004_KEY_CUSTODY_AND_CRYPTOGRAPHY.md)
for the most important document in the repository.

## What Bheka will never ship

These are permanent, contractual, and the basis of the product's positioning. They are not
a roadmap of features we have not got to yet.

1. A hidden, invisible, or disguised agent
2. Webcam capture
3. Ambient microphone capture
4. Installation on employee personal devices
5. Remote takeover of an employee machine
6. Emotion, sentiment or loyalty scoring of individuals
7. Automated adverse employment decisions
8. Silent Tier 3 activation

Full reasoning in [`docs/000_PROJECT_CONSTITUTION.md`](docs/000_PROJECT_CONSTITUTION.md).

## A warning about using this with customers

This repository is **internal**. It contains threat models, which are a map of where to
attack the platform, and commercial unit economics.

Do not send it to a customer. An enterprise security review wants a completed CAIQ or
SIG Lite questionnaire, a data flow diagram, a penetration test summary and a subprocessor
list. Those are separate, derived, redacted artifacts. They are not in scope for v1.0 of
this blueprint and should be produced when the first enterprise deal requires them.

## Known dependencies that gate this blueprint

These are the things that must resolve before large parts of this document stop being
guesses. They are tracked in `docs/030_RISK_REGISTER.md`.

1. **Fifteen discovery interviews** with South African CISOs and Information Officers.
   Until these happen, the detection rule library and the pricing are hypotheses.
2. **Attorney review** of the POPIA lawful-basis model and the RICA exposure analysis.
3. **ECT Act Chapter V cryptography provider registration** with the Department.
   Supplying cryptography products in South Africa without it is an offence.
4. **Apple Endpoint Security Framework entitlement.** Reported waits of eight to thirteen
   months with no status visibility. macOS parity is gated on this.
5. **EV code signing certificate** issuance, three to five business days validation.

Nothing in `docs/` is a substitute for any of the five.
